## 四、核心算法

> 完整推导见 `Algorithms_CN.md`；本节为面向协作开发的归纳（管线 / 规则 / 不变量 / 性能）。

### 4.1 总体管线（四阶段）

```
阶段一  按结构类型分派 (n, r, d, t)
   ↓
阶段二  饱和链烃骨架生成（基于整数划分的有根树枚举，DFS + 质心去重）
   ↓
阶段三  不饱和度处理（环：迭代加边；三键；双键）—— BFS 逐层去重
   ↓
阶段四  两阶段去重（WL 哈希分桶 → 度签名预过滤 → VF2 精确同构）
```

**表示形式递进**（逐级丰富，各阶段主导不同表示）：

```
规范字符串  "C(C,C(C))"  →  邻接表 {0:[1,2],...}  →  属性分子图 nx.Graph  →  去重桶 {WL_hash: [G,...]}
   （阶段二·DFS 树枚举）      （阶段二→三 桥梁）        （阶段三·键插入）          （阶段四）
```

### 4.2 阶段一：结构类型分派

按「环数 r、双键数 d、三键数 t」分解，各路径使用针对其化学约束优化的算法：

| 条件 | 处理路径 |
|---|---|
| `r=0 ∧ d=0 ∧ t=0` | 饱和链烃（烷烃树枚举） |
| `r=0` | 无环多烯炔（分层递推插键） |
| `r=1 ∧ t=0` | 单环多烯 |
| `d=0 ∧ t=0` | 多环烷烃（迭代加边建环） |
| 其它 | 通用情形（多环骨架 + 顺序插键） |

> 分子式到 `(r, d, t)` 的映射由 `utils.parse_molecule_input` → `_enumerate_rdt_combinations` → `_rdt_to_mol_type` 完成。

### 4.3 阶段二：骨架生成（DFS + 质心去重）

**基于整数划分的有根树枚举**（唯一的 DFS 组件，两阶段递归）：

1. **整数划分**：枚举非递增序列 `(s₁ ≥ s₂ ≥ … ≥ sₖ)`，满足 `Σsᵢ = n−1`、`k ≤ max_branches`；非递增约束天然消除顺序重复。
2. **笛卡尔积组装**：对每个划分递归求子树枚举，取笛卡尔积，**排序子串后拼接**为规范字符串：
   `canon = "C(" + join(",", sort(child_canons)) + ")"`。
3. **记忆化缓存** `(n, max_branches)`；子树调用使用 `max_branches−1`（子树根已占用一个价键）。

**质心去重**（`ProcessSymmetry`，消除"同一自由树因定根不同而产生多棵有根树"的冗余）：

| 最大子树规模 vs `⌊n/2⌋` | 处理 |
|---|---|
| `<` | 根为**唯一质心** → 保留 |
| `=` | **双质心**（n 为偶数）→ 于该子树重新定根得 `t'`，取 `min(canon(t), canon(t'))` |
| `>` | 根**非**质心 → 丢弃 |

### 4.4 阶段三：不饱和度处理（BFS 逐层去重）

| 算法 | 场景 | 策略 |
|---|---|---|
| 迭代加边 | 建环 | 每轮枚举**不相邻且度 ≤ 3** 的节点对加单键，逐轮去重 |
| 分层递推 | 无环插键 | 以不饱和度 α 分层：`L_α ← {L_{α−1} 加双键} ∪ {L_{α−2} 加三键}`（双键 Δα=1，三键 Δα=2）|
| 顺序插键 | 多环插键 | **先插入全部三键，再插入全部双键** |

**关键理由**：

- **环构造用 BFS**：同一 r 环图可由多个 (r−1) 环前驱得到，逐层去重避免组合爆炸；正确性依据是「连通 r 环图去除 r 条边必得树」。
- **三键优先**：三键化学约束更严格（sp 碳度 ≤ 2、不可与其他重键共存），可达位点少；优先插入可最大化可达搜索空间。

### 4.5 化学验证规则（每次键插入均施加）

| 约束 | 规则 | 化学含义 |
|---|---|---|
| 四价性 | `bond_load ≤ 4` | 碳最多四次成键（单=1 / 双=2 / 三=3） |
| sp 碳直线性 | `n_triple > 0 ⇒ degree ≤ 2` | sp 杂化碳最多 2 个 σ 键 |
| 禁止累积双烯 | `n_double ≥ 2 ⇒ degree ≤ 2` | 排除不稳定的 `=C=` 累积构型 |
| sp / sp² 互斥 | `n_triple > 0 ⇒ n_double = 0` | 同一碳上 sp 与 sp² 不可共存 |

### 4.6 阶段四：去重管线（本项目最关键的正确性机制）

**三级递进**：`WL 哈希分桶 → 度签名预过滤 → VF2 精确同构`。

| 机制 | 适用域 | 复杂度 |
|---|---|---|
| 基于质心的树去重 | 无环树（烷烃） | O(n) |
| 邻接表规范化（排序元组） | 度数 ≤ 4 的树 | O(n log n) |
| WL 哈希 + VF2 同构 | 带键类型的通用分子图 | O(d·m) + VF2 |

- **WL 哈希**：`nx.weisfeiler_lehman_graph_hash(G, edge_attr='bond_type', node_attr='label')`，默认 3 轮颜色细化。**哈希不同 ⇒ 必定不同构**（哈希相同则需 VF2 复核）。
- **度签名快速过滤**：VF2 之前先比较排序度序列，可消除约 80% 非匹配项。
- **VF2**：`nx.is_isomorphic(..., node_match=label, edge_match=bond_type)`，仅在冲突桶内成对调用。

**统一入口**：`utils.dedup_add_to_buckets(G, mol_type, buckets, node_match, node_label_fn, node_sig_fn, canon_key_fn, degree_signature_fn)` —— 各生成器通过参数注入节点特征编码（`label` / `halogen_counts` / `oxo_counts`），保证含氧、卤代、含氮共用同一去重语义。

> **不变量（不可破坏）**
> 1. **碰撞安全**：同一 WL 哈希必须经 VF2 **全属性同构**确认才判为重复。**禁止用裸 `set` 做同构去重**（历史上曾因 WL 哈希碰撞误删真实结构，C7H8O2 曾少 170 个）。
> 2. **图口径计数**：凯库勒式（双键位置不同的两种表示）在数学口径下是**不同的图**，**刻意保留不去重**（例：C8H8O2 + 苯环 严格口径 40 图 = 34 个唯一分子，属预期）。这与 MAYGEN 的"一分子一条 SMILES"口径不同，是**特性而非缺陷**。

### 4.7 含氧生成策略（`oxygen/unified_oxo_generator.py`）

核心思想：**骨架不饱和度下探 + 骨架 O 修饰 + 数学口径过滤**，与八隅律/数学完备口径对齐。

| 机制 | 对不饱和度 k 的影响 | 说明 |
|---|---|---|
| 骨架 k 下探 | —— | 主循环枚举 `k_skel ∈ [max(0, k_min−n_oxygen), k_max]`；低 k 骨架 + 提升组合出目标 k 的含羰基结构 |
| `=O` 取代 | **+1** | 醛 / 酮 / 羧酸 / 酯的来源 |
| 羟基 `-OH` | 0 | 醇 / 酚 |
| 醚桥（1 O） | 0 | `C-C → C-O-C` |
| 过氧桥（2 O） | 0 | `C-C → C-O-O-C`；亦支持 `C=C → C-C + O-O` |
| 双醚桥（2 O） | **+1** | `C-C → C-O-C-O`（4 元 1,3-二氧杂环） |
| 环氧插入 | 单键式 **+1** / 双键式 0 | 3 元 `C-C-O` 环 |
| 氢过氧取代基 `R-O-O-H` | 0 | 数据模型零改动 |
| O 在环（oring） | 视情况 | 跨 C 迭代；上限保护 `_ORING_MAX_ATOMS = 10` |
| 片段路径 | —— | "片段 − O − 侧链"合并（约束模式下生成醚/酯）|

- **片段严格校验**：约束模式下 `add()` 收口处对每个产物做 `graph_contains_fragment(g, fragment_name)`（VF2 子图同构），**片段被 O 机制破坏后即剔除**（如苯并被氧杂化后不再算"含苯环"），保证命令行与 GUI 计数一致。
- **过滤口径双模式**（`oxygen/chem_filter.py`）：`'math'`（**默认**，仅保留价态硬规则 C≤4 / O≤2，移除偕二醇/累积烯酮等稳定性启发式）与 `'chem'`（全部规则）。
- **预置片段库**（17 种，`fragment_library.py`）：芳香环（苯环、萘、蒽、菲、联苯）/ 杂环（呋喃、2H-吡喃、1,4-二氧六环、THF、环氧乙烷）/ 饱和环（环丙烷~环己烷）/ 多环饱和（降冰片烷、金刚烷）/ 碳链（乙基）。
  > 注：`PROJECT_GUIDE.md` 记为 16 种，系未计入"碳链·乙基"这一预留项；代码注册表实际为 **17** 条。

### 4.8 含氮生成策略（`Nitrogen/generator.py`）

- **价态口径**：中性八隅律 **C=4 / N=3**（与 MAYGEN 默认价态表一致）。
- **氮规则 DBE**：`k = nC − nH/2 + nN/2 + 1` ⟺ `nH = 2·nC + nN + 2 − 2k`。
- **三种树机制**：

| 机制 | 操作 | 对 k | 覆盖目标 |
|---|---|---|---|
| A：C→N 替换 | 在 (nC+nN) 碳骨架中选 nN 个 C 替换为 N（键型不变，每替换位 H−1） | 不变 | 含 N 杂环（吡啶←苯）、叔胺中心、亚胺 C=N、腈（←末端炔）、偶氮 |
| B：端基 N | 在 H 位挂端基 | `-NH₂`: 0 / `=NH`: +1 / `-C≡N`: +2 | 伯胺、亚胺端基、腈端基 |
| C：桥 N | 在 C-C 键插入 N | `-NH-`: 0 / `-N=C-`: +1 | 仲胺桥、亚胺桥 |

- **验证锚点**：12 个公式的预言机计数与 MAYGEN **完全一致**（如 C5H5N=685、C6H5N=4394）；≤6 重原子公式树机制覆盖率 **100%**。

### 4.9 完备性预言机与边界分析

- **原子矩阵目标 H 剪枝枚举**（`atomic_matrix_gen.py` / `atomic_matrix_n.py`）：按目标氢数做邻接矩阵全图枚举，八隅律价态模型下**数学上与 MAYGEN 等价**，作为内部**完备性预言机**。
- **边界定义**：`边界 = 完备集合 − 树机制集合`；`内部覆盖率 = |树 ∩ 完备| / |完备|`。
- **性能关键**：回溯中施加"单新键类型内前缀序"约束（原子按编号顺序首次成键），消除约 `N!` 倍标号冗余 —— 实测 C6H8O 317s → 28s（~11×）、C6H10O 139s → 14s。
- CLI：`python tools/boundary_report.py C7H6O2 [--top-missing N] [--max-atoms 8]`

### 4.10 分子式一致性门禁（单一事实源）

```python
utils.graph_formula_parts(G)          # 从图统计 (nC, nH, nO, (f, cl, br, i))，不信任调用方碳数
utils.formula_matches_input(G, ...)   # 门禁判定
structure_filter.filter_by_expected_formula(...)   # 统一兜底过滤（三条路径收口）
```

- 在 `Main.py::_generate_in_background` 的"统一后置过滤层"**之后**调用，纯烃 / 含氧 / 卤代三路统一收口。
- 字符串条目经 `to_graph_fn(mol_type, data)` 转图校验，转图失败保守剔除；幂等、纯函数。

### 4.11 性能优化汇总

| 手段 | 效果（实测） |
|---|---|
| 进程池并行（`use_parallel`，原子数 ≥7 且 `k_skel` ≥2 自动启用） | C7H8O2 无约束 **327s → 114~151s**（**2.17×**）；进程池不可用时自动回退串行 |
| 快速生成模式（`enable_oring_cross_c=False`） | C7H8O2 **327s → 129s**（2.5×）；代价约少 3% 结构（稠合 O 杂环） |
| `add()` 门禁前移 | 公式门禁先于 WL 哈希，拦截 `k+1` 溢出候选，省去哈希开销 |
| 碰撞安全去重（`_seen_add_safe`） | 修复 WL 哈希碰撞误删（C7H8O2 找回 170 个真实结构：99622 → 99792） |
| 骨架缓存 `lru_cache` | 跨 `generate()` 调用复用（GUI 重复生成同一分子式时生效） |
| 预言机有序生成前缀序约束 | C6H8O 317s→28s、C6H10O 139s→14s、C5H8O2 78s→10s |
| 列表批量插入 + 标签惰性计算 | 10 万行列表约 1.6s 渲染；官能团标签后台分块计算不阻塞 UI |

**规模参考**：C11 生成时每层最多 **90,111** 个中间图；两阶段去重管线较朴素两两比较**减少约 3–4 个数量级的 VF2 调用**。

**覆盖率参考**：C7H6O2 内部覆盖率（数学口径）**≈ 98.69%**（演进：89.9% → 93.2% 环氧 → 98.47% OOH/过氧 → 98.69% 双醚桥）。

### 4.12 坐标计算与渲染

- **3D 坐标**：RDKit ETKDG 嵌入 + MMFF 优化；≥13 碳采用**多种子策略**择最小 C-C 键长构象；含键长松弛 `_relax_bond_lengths` 与累积双键修正。相关函数定义在 `Main.py` **模块级**。

#### 8.3.1 ⚠ 硬规定：移动三查（路径一变就必须执行）

**为什么单独立一条**：改动文件**内容**不会让 Git 索引与代码里的引用失配；改动文件**位置**会**同时**打破两者，
而两者的失败都是**静默的**——不报错、不影响本机运行，只在**别人打开仓库、或有人点开那个链接**时才暴露。
本项目已**两次**踩同一类坑（§12.2 断链、§12.3 丢文件），所以要把它从"靠运气"变成"必做流程"。

| 步骤 | 命令 / 动作 | 必须看到的结果 |
|---|---|---|
| **① 归一索引** | `git add -A` | 不再出现 `?? <新路径>` 与 ` D <旧路径>` 成对存在 |
| **② 复核重命名** | `git status` | 显示 **`renamed: 旧路径 -> 新路径`**。若显示为 `D` + `??` 两行，说明路径变更未被识别 → **停手上报，不要提交** |
| **③ 复查引用** | 按下方清单逐项核对 | 所有引用新路径的地方均已同步；无 404 / 无"文件不存在" |

**第 ③ 步的复查清单**（按项目实际涉及面取用）：

| 位置 | 查什么 | 本项目的典型例子 |
|---|---|---|
| Python 代码 | 相对路径 `open()` / `Path()`、`sys.path` 插入、`os.chdir()` | 13+ 文件硬编码 `dirname(dirname(abspath(__file__)))` 求项目根 |
| 文档 | Markdown `![](相对路径)`、HTML `<img src>`、正文里提到的文件名 | `README.md` 的 `<img src="Instruction Data/截图.png">`（移动 README 时断过一次） |
| 打包配置 | `.spec` 的 `datas` / `pathex` / `hiddenimports` | `datas=[('original_programs','original_programs'), …]` |
| CI | `.github/workflows/*.yml` 的工作目录与脚本路径 | 工作流直接 `pyinstaller *.spec`，**假设仓库根 = 构建根** |
| `.gitignore` | 新位置是否**仍**被正确忽略，或**不再**被意外忽略 | `skills/`、`MAYGEN/` 移入移出时的跟踪状态 |
| 外部工具路径 | 写死的 JAR / 数据目录 | `tools/maygen_validate.py`、`Nitrogen/maygen_compare.py` 中的 MAYGEN JAR 路径 |

> **适用范围**：仅**路径变动**（移动、重命名、删除、目录重组）。只改内容、不动路径的提交**不需要**这一步。
> **谁执行**：**改路径的人**执行，不是 review 的人。Agent 也同样适用——**Agent 只暂存不代提交，但暂存前必须先跑完三查并汇报结果**。

#### 8.3.2 机器执行：`tools/move_check.py`

三查是人工判据，容易被"我觉得没问题"糊过去。故提供一个**可执行、带退出码**的检查器：

```bash
python tools/move_check.py            # 三查全跑；exit 0 = 可提交，exit 1 = 必须处理
python tools/move_check.py --quiet    # 只输出问题与结论（适合脚本/习惯性快跑）
python tools/move_check.py --refs     # 只做第 ③ 步引用检查
```

它把三查判定为：

| 检查项 | 触发条件 | 对应事故 |
|---|---|---|
| ① 未归一的重命名 | 某文件已从工作区消失、**内容完全相同**的一份却以未跟踪/被忽略状态出现在别处 | 忘记了 `git add -A` ⇒ 提交后"旧文件被删 + 新文件丢失" |
| ① 有意的移出跟踪 | 暂存删除的路径**已被 `.gitignore` 覆盖** | 这是正常的 `git rm --cached`，不报错 |
| ② RD 形态 | 重命名已暂存，但**新路径在工作区不存在** | §12.3 差点静默丢文件 |
| ③ 引用失配 | Markdown 链接 / `.spec` 的 `datas` / CI 脚本路径指向不存在的文件 | §12.2 README 配图断链 |
| ③ 旧路径残留 | 旧**目录名**（该目录已消失）或旧**文件名**仍被跟踪文件引用 | 目录重组未收尾 |

设计上刻意**宁可漏报也不误报**：判据收紧到"只在确凿时才报"，因为一个常驻误报的检查器会被直接无视。
已知边界（反引号内容不查、裸写文件名不算引用、改内容的移动降级为警告等）写在脚本头部注释里，**用前请读一遍**。

> **判据必须钉住**：`tests/test_move_check.py` 用独立临时仓库复现 14 组现场，覆盖"该拦的"与"该放行的"两类，
> 其中 **3 条是判据回归**（反引号内的示例路径、围栏代码块内的路径、代码注释里裸写的文件名 —— 三者都曾误报）。
> **改了 `move_check.py` 就必须跑它**：`--smoke`（13 项，秒级）/ 完整档（24 项）。

## 十、Gaussian 输入卡（.gjf）导出规范化

> **执行方**：WorkBuddy ｜ **日期**：2026-09-20 ｜ **状态**：已实现 + 已自测，**待真机提交验证**
>
> **背景**：v1.1.0 的 `.gjf` 导出把 `# 分子式 类型 Isomer #N` 写在**第 1 行**。
> 该行占据 Gaussian 的 **route section** 位置，Gaussian 会把 `C6H6` / `alkene`
> 当关键词解析并报 `GAUSSIAN_PARSE_INPUT_FAILURE`。GaussView 容错（只读坐标，
> 不解析关键词），所以此前「GaussView 验证通过」**掩盖了该缺陷**。
> 依据：Gaussian 官方 `Geom` 文档（`Geom=Connectivity` 段）与本仓库
> `skills/skills-hpc-gaussian-.../references/input-and-link0-matrix.md`。

### 10.1 改动清单

| 文件 | 类型 | 说明 |
|---|---|---|
| `gaussian_export.py` | **新增（根目录）** | `.gjf` 生成的**唯一出口**：块序拼装 + 配置持久化 + 连通性可靠性守卫 + 结构自检 `validate_gjf()` |
| `Main.py` | 修改 | `_generate_gjf_content` / `_generate_isomer_content` 收口到 `build_gjf`；新增模块级 `_graph_from_adjacency()`；新增 `_get_gjf_settings` / `_log_gjf_warnings` / `_open_gjf_settings_dialog`；`viz_frame` 新增「Gaussian 设置」按钮；导出前重读配置 |

### 10.2 格式对照（旧 → 新）

| 项 | 旧实现 | 新实现 |
|---|---|---|
| 第 1 行 | `# C6H6 alkene Isomer #1` ← **被当 route 解析** | `%Chk=... / %Mem / %NProcShared`（Link 0） |
| route | 缺失（无 `#` 关键词行） | `#p B3LYP/6-31G(d) Opt Geom=Connectivity` |
| 标题 | 第 3 行 `# ... - Isomer #1`（以 `#` 开头） | 纯文本一行 `C6H6 alkene Isomer #1` |
| 电荷/多重度 | 硬编码 `0 1` | 可配置，默认 `0 1` |
| 连通性块 | `M N Order 0.0 0.0 0.0`（**语法错误**）且 route 未声明 → **Gaussian 直接忽略** | `M N1 Order1 N2 Order2 …`（官方语法），route 声明 `Geom=Connectivity` |
| 连通性对称性 | 仅单向 | 双向对称（碳行列其氢、氢行列其碳） |
| 文件换行 | 依赖平台 | 固定 `\n`（`newline='\n'`，避免 CRLF） |

### 10.3 连通性块：为什么以前「写了等于没写」

`Geom=Connectivity` 是一个**路由关键词**；只有 route 段声明它，Gaussian 才会去读
坐标段之后那一块连通性数据。旧 route 段根本没有关键词（因为第 1 行被标题占了），
所以那几十行连通性数据被 Gaussian **整体跳过**；且其行格式
（`M N Order 0.0 0.0 0.0`，6 列）本身也不符合官方语法
`M N1 Order1 [N2 Order2 …]`（*"requires one line of input per atom"*）。
两个问题叠加的后果是：**用户以为键级已传给 Gaussian，实际以距离感知为准**。

### 10.4 可靠性守卫（本改动的核心设计）

连通性块把键级**写死**交给 Gaussian，写错比不写更糟。因此 `build_gjf` 在输出
连通性前依次施加三道守卫，**任一不过就整体降级**为「不输出块 + route 不带
`Geom=Connectivity`」，由 Gaussian 自行按距离感知（此时文件仍完全合法）：

| # | 守卫 | 判据 | 拦截的真实故障 |
|---|---|---|---|
| -1 | 键级可信 | 每条边必须显式带 `bond_type` | 若把 `C=C` 猜成单键提交，等于给 Gaussian 错误电子结构 |
| 0 | 索引可对齐 | 图中每个重原子都必须在坐标字典中 | 坐标缺失会导致原子编号整体错位 |
| 1 | 几何合理 | 每个 H 到最近重原子的距离 ≤ 1.4 Å | 2D 回退坐标 / 嵌入失败时 H 位置不可信 |
| 2 | 氢数自洽 | 按最近重原子归属的氢数 == 价态推算氢数 | H 坐标与图不同源（旧实现依赖「按碳序、每碳 `4−键负载` 个氢」的隐式假设） |

守卫 1、2 把旧实现「信任 RDKit 追加顺序」改成**按空间距离判定母原子**，
消除了对上游 H 排列顺序的隐式依赖。实测真实坐标下 C-H 距最近重原子
**max = 1.090 Å**（正是 `_scale_ch_bond_lengths` 的目标键长），远低于 1.4 Å 阈值。

**配套改动**：`Main.py` 新增 `_graph_from_adjacency()`，对
`_SINGLE_BOND_ONLY_TYPES = {alkane, cycloalkane, multcycloalkane}` 显式标注
`bond_type='single'`（化学上确定）；其余类型从规范字符串还原图时**不标注**，
交由守卫 -1 降级 —— 因为规范字符串不携带键级信息，猜成单键会引入错误。

> 实测前提：`GeneratorManager.generate_all()` 产出的**非烷烃**图，其每条边均已带
> `bond_type`（C4H8 / C4H6 / C6H6 全类型抽查，缺失 0 条）；仅 `alkane` 返回规范字符串。

### 15.3 预言机并行化（前缀切分 + 进程池 + 父进程去重）

**设计**：
1. `generate_for_target_h(target_h, prefix=...)`：位置 0..k−1 的键级取值固定；
2. `_replay_prefix()`：把前缀回放到矩阵状态（与主回溯**同一套规则**校验，单一事实源）；
3. `enumerate_prefixes(depth)`：枚举全部合法前缀（互不重叠，并集 = 全空间）；
4. `generate_for_target_h_parallel()`：前缀 → 进程池 worker 各自枚举子树 →
   父进程用 **WL 哈希分桶 + VF2 精确同构**跨子树合并去重；
5. 进程池不可用时**可见告警**后串行兜底（结果不变）。

**三个踩坑（都已修）**：
- **前缀深度不能"越深越好"**：合法前缀数会饱和（C6H5N 深度 1..5 仅 4/13/20/24/27 条），
  按"前缀数 ≥ 4×workers"无限加深会把**前缀枚举本身**变成主成本 → 改为
  **深度硬上限 4** + 目标「≈2×workers」；
- **Windows spawn 要求主模块带 `__main__` 守卫**：否则子进程重跑主模块 →
  `BrokenProcessPool` → 触发兜底静默退回串行（曾据此**误判"并行无加速"**）；
  测试脚本与 GUI 入口均已确认带守卫（`Main.py` 末尾有 `freeze_support()`）；
- **进程池启动成本 ~8~9 s**（spawn 重导入 networkx 等）：小公式开池反而更慢
  （C4H9NO 串行 1.3~2.8 s vs 开池 9.5 s）→ 用**探测一个子树 + 外推**自动决策，
  且探测结果被复用（不浪费）。

**等价性**：跨子树确实存在**真同构重复**（有序生成只"减少"而非完全消除标号冗余：
C4H9N 深度 1 的 4 棵子树间有 41 条同构重复）→ **父进程去重是必要的**；
实测并行唯一图集合与串行**逐元素一致**（哈希 + VF2 双向核验）。

> **触发**：用户反馈"生成含氮分子时出现 bug"（未记清触发条件）→ 做系统性 GUI 全链路排查。

### 18.1 排查方法

Tk 回调里的异常**不会崩界面**，只打 stderr —— 这是"偶发 bug"最典型的藏身处。
故搭建 **GUI 全链路 harness**：
- 真实 `root.mainloop()` 驱动（否则工作线程里的 `root.after` 会抛
  `RuntimeError: main thread is not in main loop`，属测试环境假象）；
- 劫持 `root.report_callback_exception` **捕获所有 Tk 回调异常**；
- 劫持 `_show_error` / `messagebox.*` 记录弹窗；
- 包装 `_update_isomer_list` 与 `_generate_in_background` 以判定"是否真的启动了生成"
  （避免把"生成极快完成"误判为"提前返回"）。

### 18.3 发现并修复的 2 个缺陷

**缺陷 1（§17 引入）：基团构建模式仍走"完整枚举"的上限检查与耗时预估**
- 现象：勾选基团后生成 `C6H5NO2` 会**多弹一次**"含氮枚举耗时提示"，且**白等约 2.5s**
  预估探测（估计函数按完整枚举空间探测，与构建模式无关）。
- 根因：`_generate_isomers` 中"重原子上限预检 + ETA 预估 + 确认框"只判断了
  `n_nitrogen > 0`，未排除 `_group_counts`（构建模式）。
- 修复：条件改为 `if n_nitrogen > 0 and not _group_counts:`。
- 验证：基团模式确认框数量 `2 → 1`，耗时 2.6s → **0.9s**。

**缺陷 2（§17 引入）：流式回调存在**跨线程操作 Tk**的违规**
- 现象：生成过程中/结束后，状态栏可能偶发异常或被覆盖成"计算中... 已发现 N 个结构"；
  严重时可触发 `RuntimeError: main thread is not in main loop`（Tk 非线程安全）。
- 根因：`_stream_flush()` 在**工作线程**里**直接调用** `_stream_show()`（读写
  `status_var` / `progress_label`），未经过主线程派发。
- 修复：① `_stream_flush` 改为 `root.after(0, self._stream_show, n)` 派发；
  ② `_stream_show` 增加守卫——生成已结束（按钮恢复可用）时**不再覆盖**最终状态栏。
- 验证：C5H5NO（7687 结构，33.1s，流式回调多次触发）结束后等 2.5s，
  状态栏仍为"已生成 7687 个异构体（含1N + 1O）"、进度为"完成，共 7687 个异构体"，
  无 Tk 回调异常；缓存命中 3.8s 同样正确。

### 18.4 观察（非缺陷）

- 提前返回（拒绝/警告/非法式）时，列表仍显示上一次生成结果、状态栏保留旧值 ——
  属既有交互行为（未清空列表），不影响正确性；如需"清空并提示"可另行增强。

### 18.5 回归

`test_special_groups` 41、`test_speedup` 42、`test_funcgroup` 41、
`Nitrogen.validate --anchors` 全通过（单次最长 55.9s）。

## 十九、UI 布局重构：可拖拽分栏 + 折叠面板 + 布局记忆（2026-11-07）

> **执行方**：CodeBuddy ｜ **状态**：已完成 + 已验证
> **触发**：用户反馈"非最大化时，生成异构体后分子显示框完全无法显示"，并要求
> "把 UI 中各个功能框从锁定状态改为可调整状态"。

### 19.1 诊断（改造前实测）

| 窗口 | 结果区可用高 | 键线式 Canvas | 结构信息文本 |
|---|---|---|---|
| 900×700（原默认） | 152px | 450×**83px** | **1×1，mapped=0（完全未显示）** |
| 1280×800 | 252px | 545×183px | **1×1，mapped=0** |
| 1600×900 | 352px | 625×202px | 608×81px |
| 1920×1040 | 492px | 705×202px | 688×221px |

**三个根因**：
1. **顶部"分子输入"区请求高 238~345px、请求宽 930px**（§十七 新增的基团面板 11 个复选框 +
   固定 `wraplength=820` 的提示 label 把宽度撑到窗口之外），把高度预算吃掉；
   `main_frame` 只有结果区可伸缩 → 矮窗口下结果区被压到 ~150px。
2. **右侧信息区刚性**：Canvas 硬请求 `width=300/height=200`、`ScrolledText` 默认 24 行，
   info 区请求 **779px**；空间不足时文本区被挤成 **1px 且 unmapped**（即"显示框消失"）。
3. **左右分栏是 grid 固定 3:1**，用户无法拖动，窄窗口下只能靠"谁请求大谁赢"。

### 19.2 改造内容

| # | 改动 | 说明 |
|---|---|---|
| 1 | 左右分栏 → `ttk.PanedWindow(HORIZONTAL)` | 初始 62%，可鼠标拖动；左列表右信息 |
| 2 | 右侧内部 → `ttk.PanedWindow(VERTICAL)` | 上=键线式、下=结构信息；初始 60% |
| 3 | Canvas 去掉固定请求尺寸 | 改 `width=1,height=1` + `fill=BOTH/expand`，随分栏伸缩 |
| 4 | 基团面板**默认折叠** | 常驻一行开关 + "已选: 硝基×1"摘要；展开后按宽度**流式换行**，提示文案折行宽度自适应 |
| 5 | 顶部内边距压缩 | main 15→10、title 15→8、input 10→6、result/viz 10→6 |
| 6 | 窗口尺寸 | 默认 900×700 → **1100×760**，最小 800×600 → **900×660** |
| 7 | 键线式**按 Canvas 实际尺寸渲染** | 原固定 380×220 再缩放；现按画布出图，尺寸变化 **300ms 节流重绘**，图片垂直居中 |
| 8 | 双击分隔条复位 | 左右 62% / 上下 60% |
| 9 | 布局记忆 | `~/.hydrocarbon_generator/ui_layout.json` 保存窗口尺寸 + 两个 sash；启动仅恢复**尺寸**（忽略位置，避免跑出屏幕），越界自动回退 |

**两个实现坑（已踩过并修正）**：
1. **不能用子控件"请求尺寸"决定初始 sash**：Canvas 请求仅 1px → 上栏塌成一条缝
   （实测 canvas=1×1）。必须**映射后显式 `sashpos()` 按比例设置**。
2. **钳制公式必须保证结果合法**：曾写 `max(120, min(target, total-90))`，
   当 total<210 时算出越界值 → `sashpos` 静默失效 → 回到 1px。改为
   `total<160 → 对半分`，否则 `max(70, min(60%, total-70))`。
3. 拖动分栏会连续触发 `<Configure>` → 重绘**必须节流**（300ms + 尺寸差 <12px 忽略）。

### 19.5 遗留

1. `ttk.PanedWindow` **不支持 pane 最小尺寸**：只能靠"初始比例 + 越界钳制"兜底，
   用户仍可把某一栏拖到很窄（建议后续加"重置布局"按钮或拖动时钳制）；
2. 布局记忆**不恢复窗口位置**（刻意：避免多显示器切换后窗口跑到屏幕外）；
3. 若显示器 < 900×660，可再提供"紧凑模式"（隐藏标题/压缩按钮行）；
4. 3D 可视化仍是独立 matplotlib 窗口，不参与分栏（本轮未改）。
